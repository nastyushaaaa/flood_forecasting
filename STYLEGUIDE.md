# Руководство по стилю проекта flood_forecasting

Правила, по которым мы пишем код и проводим code review. Охватывают четыре темы:

1. [Формат файлов и структура проекта](#1-формат-файлов-и-структура-проекта)
2. [Документирование API и интерфейсов](#2-документирование-api-и-интерфейсов)

За основу взяты [PEP 8](https://peps.python.org/pep-0008/), [PEP 257](https://peps.python.org/pep-0257/),
[Google Python Style Guide](https://google.github.io/styleguide/pyguide.html) (формат докстрингов),
[Google JavaScript Style Guide](https://google.github.io/styleguide/jsguide.html) и документация FastAPI.
Здесь записано только то, что мы уточнили или выбрали для себя. По всему остальному действуют эти руководства.

У каждого правила есть номер. В замечаниях на ревью ссылаемся на него, например: «п. 4.1».

## 1. Формат файлов и структура проекта

**1.1. Кодировка и переводы строк.** UTF-8 без BOM, переводы строк LF, в конце файла один перевод строки,
без пробелов в конце строк. Настройки лежат в `.editorconfig`, его понимают VS Code (с расширением EditorConfig) и PyCharm.

**1.2. Отступы и длина строки.**

| Язык | Отступ | Макс. длина строки | Кавычки |
|---|---|---|---|
| Python | 4 пробела | 120 | одинарные `'...'`, двойные — только если внутри есть одинарная |
| JavaScript, CSS, HTML, JSON | 2 пробела | 120 | JS — одинарные, HTML-атрибуты — двойные |
| Markdown | — | без ограничения (одна фраза — одна строка удобнее для диффов) | — |

Длинный вызов переносим по аргументам, длинный комментарий выносим на отдельную строку над кодом.

**1.3. Имена файлов и папок.** Только латиница, цифры и `_` (Python, данные) или `-` (JS, CSS), всё в нижнем регистре:
`hourly_forecast.py`, `forecast_khabarovsk.json`, `js/api.js`. Кириллица и пробелы в именах ломают импорт, ссылки и
командную строку на разных ОС. Названия постов пишем транслитом, как в данных: `khabarovsk`, `blagoveshchensk`.

**1.4. Структура репозитория.** Корень содержит только точки входа и общие файлы. Каждая модель или подсистема
лежит в своей папке.

```
flood_forecasting/
├── main.py                  # сервер FastAPI: точка входа, только подключение роутеров и статики
├── hourly_forecast.py       # → со временем переезжает в api/
├── <имя>_model/             # одна модель — одна папка (amur_pg_lstm, linear_model, prophet_model, ...)
│   ├── README.md            # что делает модель, как запустить, метрики (п. 2.1)
│   ├── <модуль>.py          # код, который импортирует сервер
│   ├── run.py               # скрипт обучения / пересчёта (если нужен)
│   ├── model/               # обученные веса и метрики
│   └── figures/             # графики для отчётов
├── data/                    # общие исходные данные — по одной копии (п. 1.5)
├── frontend/                # сайт: index.html, css/, js/, mock/
├── tests/                   # тесты pytest: test_<модуль>.py
├── docs/                    # презентации, отчёты, .xlsx с результатами
├── requirements.txt
├── README.md
└── STYLEGUIDE.md
```

Новый код кладём сразу по этой схеме. Отдельные скрипты в корне (`power.py`, `polynomial2.py`, `run.py` и т. п.)
переносим в папку своей модели отдельным PR, чтобы не смешивать перенос файлов с изменением кода.

**1.5. Данные в репозитории.** Каждый общий набор данных хранится в одной копии в `data/`, модели читают его оттуда.
Если модели нужен свой предобработанный файл, он лежит в `<модель>/data/` вместе с README, где сказано,
как он получен. Файлы больше 50 МБ в git не кладём, в README пишем, откуда их скачать. Результаты, которые можно
пересчитать (`predictions.csv`, графики), коммитим только если они нужны для отчёта или фронтенда.

**1.6. Что не попадает в git.** Настройки IDE (`.idea/`, `.vscode/`), `.DS_Store`, `__pycache__/`, виртуальные
окружения, `.env` с ключами. Всё это перечислено в `.gitignore`. Если такой файл уже закоммичен, удаляем его из индекса
командой `git rm -r --cached <путь>`.

**1.7. Зависимости.** Общие для сервера зависимости лежат в корневом `requirements.txt`. Зависимости, которые нужны только
одной модели (например, `torch`, `prophet`), лежат в `<модель>/requirements.txt`. Версии указываем снизу: `pandas>=2.0`.

**1.8. Порядок импортов (Python).** Три группы через пустую строку: стандартная библиотека → сторонние пакеты →
модули проекта. Внутри группы по алфавиту. `import *` не используем. Код с побочными эффектами
(`load_dotenv()`, настройка логов) идёт после всех импортов.

**1.9. Модули из блокнотов.** Если `.py` генерируется из `.ipynb` (ячейка `%%writefile`), об этом сказано в
первой строке докстринга модуля, а правки вносятся в блокнот. Сервер и другие модели импортируют только `.py`.

**1.10. Порядок внутри файла.** Python: докстринг модуля → импорты → константы (`UPPER_CASE`, с единицами
измерения в комментарии) → функции и классы (сначала вспомогательные, потом публичные) → `if __name__ == '__main__':`.
JS: шапка-комментарий о назначении файла → константы → состояние → функции → навешивание обработчиков → запуск.

## 2. Документирование API и интерфейсов

**2.1. README в каждой папке.** В README модуля описано, что он делает, как его запустить (команды целиком),
что принимает на вход и что отдаёт, какие у него метрики и ограничения. Пример: `amur_pg_lstm/README.md`.

**2.2. Докстринги Python.** У каждого публичного модуля, класса и функции есть докстринг в формате Google на русском языке:

```python
def get_level_forecast(station_id: str, days: int = 14) -> pd.DataFrame:
    """Прогноз уровня воды на посту на `days` суток вперёд.

    Args:
        station_id: код поста латиницей, например 'khabarovsk'.
        days: горизонт прогноза, сут (1–14).

    Returns:
        Таблица с колонками date, level, level_low, level_high; уровни в см над нулём поста.

    Raises:
        ValueError: неизвестный пост или горизонт вне 1–14.
        DataSourceError: источник наблюдений недоступен.
    """
```

Обязательно указываем **единицы измерения** (см, мм, °C, сут) и **форму данных** (что в индексе, какие колонки).
Для короткой очевидной функции хватает одной строки. Секцию `Raises` пишем, если функция сама выбрасывает исключение.

**2.3. Аннотации типов.** У публичных функций Python аннотированы аргументы и возвращаемое значение.
Для словарей с фиксированными ключами используем `dataclass` или `TypedDict`, а не `dict`.

**2.4. Публичное и внутреннее.** Функции, которые не предназначены для вызова извне модуля, начинаются с `_`.
Для них документация может быть короче.

**2.5. JSDoc в JavaScript.** Функции, которые вызываются из других файлов (весь `api.js`, `render...` и `draw...`),
документируем в формате JSDoc:

```js
/**
 * Краткосрочный прогноз поста: история + прогноз с коридором.
 * @param {string} stationId код поста, например 'khabarovsk'
 * @returns {Promise<Forecast|null>} null — прогноза для поста нет
 * @throws {ApiError} сервер ответил ошибкой или не ответил вовремя
 */
```

Структуры ответов сервера описываем один раз через `@typedef` в `api.js`.

**2.6. HTTP API (FastAPI).** Документация API — это автоматически сгенерированная страница `/docs`, поэтому у каждого эндпоинта есть:

- путь с префиксом `/api`, существительные во множественном числе, слова через дефис: `/api/stations`, `/api/forecast/{station_id}`;
- `summary` и docstring (он попадает в описание);
- `response_model` (Pydantic или dataclass);
- параметры через `Query(...)` / `Path(...)` с `description` и ограничениями (`ge`, `le`);
- `responses={...}` для ошибок, которые эндпоинт возвращает намеренно (п. 4.6).

```python
@router.get('/hourly-forecast', summary='Почасовой прогноз погоды', response_model=list[HourlyForecast],
            responses={502: {'description': 'Open-Meteo недоступен'}})
def read_hourly_forecast(
    latitude: float = Query(..., ge=-90, le=90, description='Широта, градусы'),
    longitude: float = Query(..., ge=-180, le=180, description='Долгота, градусы'),
    days: int = Query(3, ge=1, le=16, description='Сколько суток прогноза'),
):
    """Погода по часам из Open-Meteo для точки (используется для учёта осадков)."""
```

**2.7. Формат JSON.** Ключи в `snake_case`. Даты в ISO 8601: `"2026-08-01"` или `"2026-08-01T10:30:00+10:00"`.
Отсутствующее значение передаём как `null`, а не `0`, `-999` или пустую строку. Единицы измерения указаны в документации поля
(уровни в см). Контракт между бэкендом и фронтендом описан в `frontend/README.md` («Контракт API»). Если формат ответа
меняется, эндпоинт, контракт и mock-файлы меняем в одном PR.

**2.8. Комментарии в коде** объясняют, *почему* код написан так, а не что он делает. Магические числа выносим в
именованные константы с единицами: `SPIKE_LIMIT_CM = 40`, а не `40` посреди выражения. Закомментированный код не коммитим.

## 3. Асинхронные операции и события

### Python

**3.1. `async def` или `def` в FastAPI.** Внутри `async def` можно вызывать только неблокирующий код (`await`,
`httpx.AsyncClient`). Если эндпоинт использует `requests`, `pandas`, `torch` или читает файлы, объявляем его через
обычный `def`: FastAPI сам выполнит его в пуле потоков. `requests.get` и `time.sleep` внутри `async def` запрещены,
потому что останавливают весь сервер.

**3.2. Таймаут у каждого сетевого запроса.** `requests.get(url, timeout=(5, 30))` (подключение, чтение, в секундах).
Без таймаута запрос к зависшему сервису держит поток бесконечно.

**3.3. Повторные попытки.** Повторяем только то, что может пройти со второго раза: таймаут, обрыв соединения, ответы
`429` и `5xx`. Ответы `4xx` (кроме 429) не повторяем. Число попыток ограничено, пауза растёт экспоненциально (1, 2, 4… с),
заголовок `Retry-After` учитываем. Каждую повторную попытку пишем в лог с уровнем WARNING (п. 4.2). Если все попытки
исчерпаны, выбрасываем исключение с причиной последней ошибки (п. 4.4).

**3.4. Ресурсы.** `requests.Session` / `httpx.Client` создаём один раз на модуль или открываем через `with`.
Файлы тоже открываем только через `with`.

**3.5. Долгие операции не выполняются внутри запроса.** Обучение моделей и загрузка архивов погоды запускаются скриптами
(`run.py`) или по расписанию. Эндпоинт отдаёт уже посчитанный результат или считает быстрый прогноз по загруженной модели.
Модель загружаем один раз при старте сервера, а не при каждом запросе.

### JavaScript

**3.6. Только `async/await`.** Цепочки `.then()` с `async/await` в одной функции не смешиваем. Для каждой
асинхронной операции понятно, где обрабатывается её ошибка: либо `try/catch` в самой функции, либо в том месте,
которое её вызывает. Если обработчик события вызывает `async`-функцию и не ждёт её, эта функция сама ловит свои
ошибки. Иначе в консоли появится `Uncaught (in promise)`, а интерфейс зависнет в промежуточном состоянии.

**3.7. Таймауты и отмена запросов.** Все `fetch` проходят через одну функцию (`fetchJson` в `api.js`), где задан таймаут:
`fetch(url, { signal: AbortSignal.timeout(15000) })`. Если пользователь запустил новый запрос того же вида
(выбрал другой пост), ответ на старый игнорируем или отменяем через `AbortController`.

**3.8. Параллельные запросы.** Независимые запросы отправляем параллельно через `Promise.all`. Если ошибка одного запроса не
должна мешать показать результат другого (краткосрочный и сезонный прогнозы), используем `Promise.allSettled` и
обрабатываем каждый результат отдельно.

**3.9. События.** Обработчики навешиваем только через `addEventListener`, атрибуты `onclick` в HTML не используем.
Для элементов, которые перерисовываются (чипы, строки таблицы), используем делегирование: один обработчик на контейнере
и `event.target.closest(...)`. Обработчик короткий и вызывает именованную функцию. Всё, на что можно нажать мышью,
должно срабатывать и с клавиатуры (Enter/пробел), а для действий лучше брать `<button>`.

**3.10. Повторные срабатывания.** Пока идёт загрузка, кнопку, которая её запустила, блокируем (`disabled`)
и разблокируем в `finally`. Если обработчик частого события (`input`, `resize`, `scroll`) делает запрос или тяжёлую
перерисовку, вызываем его с задержкой (debounce) 200–300 мс.

## 4. Обработка ошибок и логирование

### Python

**4.1. `logging`, а не `print`.** В каждом модуле заводим свой логгер: `logger = logging.getLogger(__name__)`.
`print` разрешён только в блокнотах и для итогового вывода CLI-скрипта (таблица метрик). Настройку логирования
делаем один раз в точке входа (`main.py` или `if __name__ == '__main__':`), а не в библиотечных модулях:

```python
logging.basicConfig(level=os.getenv('LOG_LEVEL', 'INFO'),
                    format='%(asctime)s %(levelname)-7s %(name)s: %(message)s')
```

**4.2. Уровни.**

| Уровень | Когда | Пример |
|---|---|---|
| DEBUG | детали для отладки, по умолчанию не видны | размеры массивов, параметры запроса |
| INFO | ключевые шаги работы | «Загружено 1250 наблюдений по khabarovsk за 2025-09-01 — 2026-08-01» |
| WARNING | что-то пошло не так, но работа продолжается | повторная попытка запроса, 12 значений уровня восстановлены интерполяцией |
| ERROR | операция не выполнена | прогноз для поста не построен |
| CRITICAL | сервис не может работать | не найден файл обученной модели при старте |

**4.3. Текст сообщения.** Сообщение должно отвечать на вопросы «что произошло, с какими параметрами и что дальше».
Используем ленивое форматирование `%`, а не f-строку: `logger.warning('ERA5 %s: ответ %d, повтор %d/%d через %.0f с', name, status, attempt, retries, delay)`.
Ключи API, пароли и содержимое `.env` в логи не пишем.

**4.4. Исключения.**
- Ловим конкретные типы (`requests.Timeout`, `KeyError`). Голые `except:` и `except Exception: pass` запрещены.
- Если ловим исключение и выбрасываем своё, сохраняем причину: `raise DataSourceError(...) from e`.
- Ошибки предметной области описываем своими классами, а не общим `RuntimeError`.
  Например, `DataSourceError` (внешний источник не ответил), `InsufficientDataError` (мало истории для прогноза).
- В тексте исключения есть контекст: пост, даты, источник. «Ошибка загрузки» без подробностей недостаточно.
- Если ошибка перехвачена и работа продолжается, пишем её через `logger.exception(...)` (сохраняется трассировка)
  или `logger.warning(...)`. Молча ошибку не проглатываем.

**4.5. Проверка входных данных на границах.** Публичная функция проверяет аргументы и выбрасывает `ValueError`
с понятным текстом. Иначе пользователь получит `KeyError` из глубины pandas. Ответ внешнего сервиса проверяем
перед разбором: ожидаемые ключи есть, длины массивов совпадают.

**4.6. Ошибки HTTP API.** Эндпоинт переводит исключения в коды ответа через `HTTPException`:

| Ситуация | Код |
|---|---|
| неверные параметры (FastAPI проверяет сам по аннотациям и `Query`) | 422 |
| поста или прогноза нет | 404 |
| внешний источник (Open-Meteo, allrivers) не ответил | 502 |
| модель не загружена, сервис временно не готов | 503 |

Тело ответа: `{"detail": "понятный текст"}`. Трассировку клиенту не отдаём. Непредвиденные исключения ловит общий
обработчик `@app.exception_handler(Exception)`, он пишет `logger.exception` и отвечает 500.

### JavaScript

**4.7. Пользователь видит ошибку.** Если загрузка не удалась, на странице выводим понятное сообщение в том блоке, где должны были
появиться данные («Не удалось загрузить прогноз: сервер не ответил»), а не `alert`. Интерфейс остаётся рабочим:
кнопки разблокированы, повторить загрузку можно. Для разработчика пишем `console.error(...)` с контекстом (какой запрос, какой пост).

**4.8. «Нет данных» и «ошибка» показываем по-разному.** `null` от `api.js` означает, что данных нет, и это нормальная ситуация:
выводим нейтральное сообщение. Исключение означает сбой: выводим сообщение об ошибке. Пустой `catch {}` запрещён.

**4.9. Ошибки запросов собираются в одном месте.** `fetchJson` проверяет `response.ok`, выбрасывает ошибку с адресом и
кодом ответа, обрабатывает таймаут (п. 3.7) и некорректный JSON. Остальной код не обращается к `fetch` напрямую.

## 5. Как проводим code review

**5.1. Всё через pull request.** В `main` напрямую не пушим. Ветки называем `feature/<что>`, `fix/<что>`,
`docs/<что>`, `refactor/<что>`. Для слияния нужен минимум один approve от участника, который не писал этот код.

**5.2. Размер PR.** Ревью удобно проводить на 150–400 строках. Если PR больше, в описании указываем, какие файлы
смотреть в первую очередь. Если код переносится в другой файл, первым коммитом идёт перенос без изменений,
а правки — следующими коммитами, чтобы в истории было видно, что именно поменялось.

**5.3. Описание PR.** В описании указываем, что сделано и зачем, как проверить (команда или адрес страницы) и что
ревьюеру посмотреть внимательнее.

**5.4. Тон ревью.** Ревью — это разговор двух коллег о коде, а не оценка человека.

- Начинаем с того, что сделано хорошо, и говорим об этом конкретно («удачно, что весь обмен с сервером собран в `api.js`»).
- Замечание формулируем как предложение и объясняем, *зачем* это нужно проекту:
  «Предлагаю добавить таймаут (п. 3.2): когда подключим настоящий API, зависший запрос не заблокирует страницу».
  Не пишем «это неправильно», «переделай всё», «так не делают».
- Говорим о коде, а не об авторе: «здесь ошибка не обрабатывается», а не «ты не обработал ошибку».
- Если не уверены, задаём вопрос, а не утверждаем: «Правильно понимаю, что…?»
- Не придираемся к вкусовщине, которой нет в руководстве. Если правило кажется нужным, предлагаем добавить его сюда отдельным PR.

**5.5. Метки замечаний.** Замечание начинается с метки и ссылки на пункт руководства, если она есть:

- `[важно]`: без этого PR лучше не сливать (ошибка или нарушение правил 3.x и 4.x);
- `[предложение]`: улучшение, автор решает сам;
- `[вопрос]`: нужно пояснение.

Пример: `[важно] п. 3.2: у requests.get пока нет таймаута — если Open-Meteo зависнет, запрос будет ждать бесконечно.
Предлагаю timeout=(5, 30).` Если можем, сразу показываем вариант исправления (кнопка *Suggest changes*).

**5.6. Ответы автора.** Автор отвечает на каждое замечание: «Исправлено в `<хеш коммита>`» или объясняет, почему не согласен.
Исправления по замечаниям одного раунда оформляем отдельными коммитами, без `force push`, чтобы ревьюер видел, что
изменилось. Обсуждение закрывает (*Resolve conversation*) тот, кто его начал. Благодарить за ревью и за исправления — нормально.

**5.7. Раунды.** Раунд: ревьюер отправляет ревью (*Request changes* или *Approve*), автор исправляет и запрашивает
повторное ревью (*Re-request review*). PR сливается после *Approve*, когда все обсуждения закрыты.

**5.8. Чек-лист ревьюера.**

- [ ] Файлы на своих местах, имена и форматирование по п. 1.1–1.3, 1.8; в diff нет лишнего (п. 1.6).
- [ ] У публичных функций и эндпоинтов есть документация с единицами измерения (п. 2.2–2.7).
- [ ] У сетевых запросов есть таймауты, повторы разумные, блокирующий код не вызывается в `async` (п. 3.1–3.5).
- [ ] В JS у каждой асинхронной цепочки есть обработка ошибок, обработчики событий навешаны по п. 3.9–3.10.
- [ ] Вместо `print` используется `logging`, исключения конкретные и с контекстом, ошибки не проглатываются (п. 4.1–4.5).
- [ ] Пользователь видит понятное сообщение об ошибке, сервер возвращает правильный HTTP-код (п. 4.6–4.8).
