# Фронтенд «Уровень»: формат сайта и визуализации

Здесь собраны два решения по фронтенду: в каком формате делаем сайт и как показываем исходные данные и прогноз.
Ниже описано, как устроен код, как его запустить и в каком формате бэкенд должен отдавать данные.

Сайт повторяет дизайн-проект: «Стили и палитра» (токены) и «Дашборд 1 · Базовая светлая» (макет страницы).

---

## 1. Формат сайта

**Выбор: одна HTML-страница с CSS и JavaScript без сборки. Раздаёт её наш же сервер FastAPI, данные страница получает от него в JSON.**

| Вариант | Плюсы | Минусы |
|---|---|---|
| Streamlit / Dash (всё на Python) | быстро, без JavaScript | дизайн-проект точно не повторить: свои чипы, KPI-карточки, боковая панель, темы банков. Любой клик перезапускает весь скрипт |
| React / Vue + сборщик (Vite) | компоненты, удобно для большого приложения | нужен Node.js и сборка, команде пришлось бы осваивать новый стек. Для одной страницы это избыточно |
| **HTML + CSS + JS, раздаёт FastAPI** ✅ | макет повторяется один в один. Токены дизайна стали CSS-переменными, поэтому тема (тёмная, банки) переключается одной строкой. Ничего не надо устанавливать и собирать: правишь файл и обновляешь страницу. Сервер FastAPI уже есть в репозитории | если страниц станет много, код придётся делить аккуратнее. Тогда можно перейти на фреймворк, а API останется прежним |

Библиотеки лежат в `frontend/vendor/` (скачаны один раз), устанавливать их не нужно. Подложка карты и шрифты по-прежнему грузятся из интернета; без сети сайт всё равно работает, только без карты-подложки и с системным шрифтом.

- **Plotly.js** — для графиков. В нём есть всё, что нужно в макете: коридор неопределённости (заливка между линиями), горизонтальные линии порогов, подсказка при наведении. Это тот же Plotly, что в Python, и описание линий (`x`, `y`, `mode`, `line`) устроено так же.
- **Leaflet** — для карты постов. Маркеры у нас — SVG-значки статусов с разной формой (круг, треугольник, ромб, квадрат). Карты Plotly такие маркеры рисовать не умеют, а в Leaflet это делается в несколько строк.

## 2. Как показываем данные

Главный вопрос пользователя (сотрудника банка): **«Где вода уже опасна и где станет опасной в ближайшие дни?»**
Поэтому страница идёт от общего к частному: сначала сводка, затем география и список, затем прогноз по одному посту.

| Данные | На какой вопрос отвечает | Как показываем | Почему так |
|---|---|---|---|
| Статус каждого поста (по порогам) | «Есть ли тревога?» | красная плашка над всем остальным + 5 KPI-карточек (всего / норма / критический / пойма / опасный) | тревогу видно сразу, до любых графиков |
| Статус | — | **значок: форма + цвет** (норма ●, критический ▲, пойма ◆, опасный ■, нет данных ○) | статусы различимы при дальтонизме и на ч/б печати |
| Доли статусов | «Насколько всё плохо в целом?» | одна горизонтальная полоса 100 % + список «статус — число» | доли на полосе сравнивать легче, чем углы круговой диаграммы, особенно маленькие |
| Координаты постов | «Где это?» | карта Leaflet со спокойной серой подложкой, маркер = значок статуса | карта нужна только для ориентации, поэтому подложка не спорит с цветами статусов |
| Текущий уровень, пороги | «Сколько осталось до опасного?» | таблица: сортировка по опасности, колонка «До опасного, см» со знаком (+34 значит порог уже превышен) | точные числа удобнее читать в таблице, график для этого хуже |
| История уровня + краткосрочный прогноз (PG-LSTM, 14 сут) | «Что будет через неделю-две?» | сплошная линия — факт, пунктир — прогноз, закрашенный коридор — неопределённость, пунктиры порогов с подписями, вертикаль «сегодня», под графиком карточки на 1 / 7 / 14 сутки | ошибка модели растёт с горизонтом (4 → 24 → 42 см), и расширение коридора это показывает. Решение принимается по верхней границе коридора, поэтому в карточках виден статус именно по ней |
| Сезонный прогноз на год | «Ждать ли половодья в этом году?» | то же устройство графика, но цвет охристый, вывод дан текстом в плашке под графиком | другой цвет, чтобы не путать с краткосрочным прогнозом. Текстовый вывод нужен тем, кто графики не читает |

Общие правила для всех графиков:

- **Цвета статусов используются только для статусов.** Факт рисуем тёмным, прогноз — бирюзовым, сезонный ход — охрой. Так красный на графике всегда означает «опасный порог», а не одну из линий.
- **Пороги рисуем на каждом графике уровня.** Сам по себе уровень «412 см» ничего не говорит, пока рядом не видно, где пойма.
- **Не используем** круговые диаграммы, 3D и две оси Y на одном графике.

### Фильтры

Округ, река и статус работают одинаково: чип «Все» плюс чип на каждое значение. Один клик по реке сразу оставляет только её. Повторные клики добавляют или убирают значения, а «Все» сбрасывает фильтр. Список рек зависит от выбранных округов. Если выбранный пост скрыт фильтрами, прогноз переключается на самый опасный из показанных постов.

### Бизнес-выводы для банка

Карточка внизу страницы (`js/business.js`) переводит уровни воды на язык банка. Её содержимое зависит от фильтров «округ» и «река» и от выбранного поста. Разделы раскрываются по клику, открыта только сводка.

| Раздел | Что внутри |
|---|---|
| Сводка для руководства | уровень риска (низкий / умеренный / высокий / критический), факты по территории, вероятности по прогнозу, запас времени до порога, одно главное действие |
| Отделения и банкоматы | операционный риск: наличность, инкассация, сотрудники, план непрерывности бизнеса |
| Кредиты и залоги | кредитный риск: страховка залогов, заёмщики, зависящие от реки, кредитные каникулы, резервы |
| Оценка возможных потерь | калькулятор: кредиты под залог в зоне × вероятность выхода на пойму × доля ущерба |
| Возможности для бизнеса | до паводка: страхование и цена риска. Во время и после: кредиты на восстановление, отсрочки |

**Как считается вероятность.** Коридор прогноза 80 % считаем интервалом от 10 до 90 %. Тогда σ = (верхняя граница − медиана) / 1,28, и для каждого дня P(уровень > порог) = 1 − Φ((порог − медиана) / σ). Берём самый опасный день. Вероятность за год не может быть меньше вероятности за 14 суток.

**Уровень риска** определяется так: худший текущий статус постов территории плюс вероятности по прогнозу выбранного поста.

| Уровень | Условие (достаточно одного) |
|---|---|
| Критический | есть пост с опасным уровнем; P(опасный уровень за 14 сут) ≥ 50 % |
| Высокий | есть пост с выходом на пойму; P(пойма за 14 сут) ≥ 50 %; P(опасный за 14 сут) ≥ 20 % |
| Умеренный | есть пост с критическим уровнем; P(пойма за 14 сут) ≥ 10 %; P(пойма за год) ≥ 20 % |
| Низкий | всё остальное |

Тексты рекомендаций собраны в таблицу `ACTIONS` в начале `business.js`, их можно править, не трогая расчёты. Пороги процентов и значения калькулятора по умолчанию (1 000 млн ₽, ущерб 15 %, порог существенности 1 %) условные. Их нужно согласовать с командой.

### Исходные данные: что предлагаем добавить следующим шагом

Модель прогнозирует по уровням четырёх постов и погоде бассейна. Чтобы прогнозу доверяли, полезно показать и эти входные данные:

1. **Вышестоящие посты** (Поярково → Благовещенск → Ленинское → Хабаровск). Делаем 4 небольших графика друг под другом с общей осью времени (small multiples): видно, как волна паводка идёт вниз по Амуру с задержкой в несколько суток. Один график с четырьмя линиями не подходит: у постов разные нули, линии будут нечитаемыми.
2. **Погода** из уже готового эндпоинта `/hourly_forecast`: осадки столбиками по суткам и температура линией, на двух небольших графиках с общей осью времени, а не на одном с двумя осями.
3. **Снегозапас бассейна** (`*_swe` в датасете модели) — график-область весной: объясняет, откуда возьмётся половодье.

Все три графика встают в ту же карточку-шаблон и используют те же функции из `js/charts.js`.

## 3. Как запустить

**Вариант A — вместе с бэкендом** (из корня репозитория):

```bash
pip install fastapi uvicorn python-dotenv requests
uvicorn main:app --reload
```

Открыть http://127.0.0.1:8000/

**Вариант B — только фронтенд:**

```bash
cd frontend
python3 -m http.server 8080
```

Открыть http://localhost:8080

> Открывать `index.html` двойным кликом нельзя: браузер не даст странице прочитать JSON с диска. Нужен любой из двух серверов выше.

**Темы** задаются в адресе страницы:

- `?theme=dark` — тёмная тема для ситуационного центра;
- `?brand=sber`, `alfa`, `vtb`, `gpb`, `rshb`, `sovcom` — фирменные цвета банка.

## 4. Что где лежит

```
frontend/
├── index.html          каркас страницы: блоки макета с пустыми контейнерами (id="...")
├── css/
│   ├── tokens.css      ВСЕ цвета, шрифты, отступы, радиусы + темы (из «Стили и палитра»)
│   └── style.css       компоненты: u-card, u-kpi, u-badge, u-chip, u-btn, u-table, адаптивность
├── js/                 (подключаются в index.html именно в этом порядке)
│   ├── format.js       числа «1 384», «−74», даты «01.08.2026», склонения
│   ├── status.js       статусы: подписи, значки, расчёт статуса по порогам
│   ├── api.js          ВСЯ загрузка данных; переключатель USE_MOCK
│   ├── map.js          карта Leaflet
│   ├── charts.js       графики Plotly: прогноз и сезонный ход
│   ├── business.js     бизнес-выводы для банка: уровень риска, рекомендации, калькулятор потерь
│   └── main.js         сборка страницы: фильтры, KPI, таблица, выбор поста, выгрузка
├── vendor/             библиотеки Leaflet 1.9.4 и Plotly 2.35.2 (не редактировать)
├── mock/               тестовые данные в формате будущего API
└── tools/make_mock.py  создаёт файлы в mock/ из папки amur_pg_lstm
```

Правила, чтобы код оставался понятным:

- цвета пишем только через `var(--...)` из `tokens.css`, иначе ломаются темы;
- с сервером общается только `api.js`;
- текст из данных вставляем в HTML через `escapeHtml()`.

## 5. Контракт API (что фронтенд ждёт от бэкенда)

Сейчас фронтенд читает эти же структуры из `mock/*.json`.

### `GET /api/stations?at=2026-08-01T10:30`

```json
{
  "updated_at": "2026-08-01T10:30:00+03:00",
  "next_update_at": "2026-08-01T20:00:00+03:00",
  "stations": [
    {
      "id": "khabarovsk", "name": "Хабаровск", "river": "Амур", "okrug": "ДФО",
      "lat": 48.48, "lon": 135.07,
      "level": 405.0,
      "measured_at": "2026-08-01",
      "thresholds": { "watch": 300, "flood": 470, "danger": 550 }
    }
  ]
}
```

- `level: null` означает, что данных нет.
- Статус фронтенд считает сам по `thresholds` (функция `getStatus` в `status.js`).

### `GET /api/forecast/{id}` — краткосрочный прогноз (404, если для поста прогноза нет)

```json
{
  "station_id": "khabarovsk", "model": "PG-LSTM", "model_note": "…", "interval_label": "Коридор 80 %",
  "today": "2026-08-01",
  "history":  [ { "date": "2026-04-03", "level": -35.0 } ],
  "forecast": [ { "date": "2026-08-02", "horizon": 1, "level": 408.6, "level_low": 404.4, "level_high": 413.0 } ]
}
```

Поля `forecast` совпадают с результатом `pg_lstm.forecast()` из `amur_pg_lstm/`, преобразовывать ничего не нужно.

### `GET /api/seasonal/{id}` — сезонный ход (404, если нет)

```json
{
  "station_id": "khabarovsk", "model": "…", "model_note": "…", "today": "2026-08-01",
  "fact":     [ { "date": "2026-01-01", "level": -120.0 } ],
  "seasonal": [ { "date": "2026-08-02", "level": 268.1, "level_low": 120.4, "level_high": 455.0 } ]
}
```

**Чтобы перейти на настоящие данные:** реализовать три эндпоинта в `main.py` и поставить `USE_MOCK = false` в `js/api.js`. Больше ничего во фронтенде менять не нужно.

## 7. Открытые вопросы к команде

1. **Пороги постов.** Нужны настоящие значения «готовность / выход на пойму / опасный» для каждого поста, например из данных Росгидромета.
2. **Горизонт прогноза.** В макете прогноз на 30 дней (LightGBM), а наша модель PG-LSTM прогнозирует на 14 суток. Сейчас карточки под графиком показывают 1 / 7 / 14 сутки. Нужно согласовать с дизайнером.
3. **Сезонная модель.** В макете Prophet. Сейчас вместо него климатическая норма, а она не учитывает, что в этом году вода выше обычного. Prophet подключим, когда он будет готов.
4. **Отчёт.** Кнопка «Скачать отчёт» сейчас выгружает CSV (он открывается в Excel). Если нужен настоящий `.xlsx` с оформлением, его будет отдавать бэкенд.
5. **Подписи статуса «watch».** В макете он называется по-разному: «Критический уровень» в фильтрах и таблице и «Готовн.» на графике. Сейчас сделано как в макете, но лучше выбрать одно название.
